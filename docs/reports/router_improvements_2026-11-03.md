## 1. 記憶を必ず候補に入れる（不採用）

- 計画: 製品の `route()` は会話と記憶を必ず候補に入れるが、best-v2 は会話だけ。test の正解がツールの 121件のうち memory.request の 5件は、検索の上位8件にないので候補に入らない。検索の上位にないときに追加の候補として足し（検索の特徴は「なし」、reranker は LARM の全カードの点数）、dev で学習し直した（C は dev の交差検証で 0.1、回す閾値 0.4007）。
- 結果: 条件を満たさない（1位の差の CI が 0 をまたぐ。回す率も CI が 0 をまたぐ）。
- 根拠: 5件のうち直ったのは 1件。残る 4件（うち 3件は同じ文）は、記憶が候補に入っても LARM の ruri の記憶の点数が 0.058〜0.083 と低く、1位にならない（1位は会話、ruri の1位は read_memory 0.18）。足りないのは候補の作りではなく、reranker の記憶の点数。記憶の依頼の言い方を ruri の学習に足す（改善の候補 6）ほうが筋がよい。
- 実測: `docs/reports/data/2026-11-03/improve/c1-mem.compare.json`。コード（best-v2 の設定 `best-v2+mem`）は消した。全カードの点数を読む `--every` と比較の `compare.py` は残した。

## 2. ツールの候補を 7件から増やす（採用、2026-11-04）

- 計画: 検索（sr-corr）の全カードの順位（`srRanking`、種類の上限をかけ、会話を除く）の上位 k 件のツールのうち、検索の上位8件に入っていないものを追加の候補にする。検索の確率は「なし」（0）、検索の順位の特徴は全カードの順位、検索の点数は全カードの順位の点数（1位で割る）、reranker は LARM の全カードの点数。k は 10・12・16 から dev の交差検証（会話ごとの 5分割）の1位の正解率で選び、同じなら小さい k。
- dev: 今の構成 85.3%、k=10 85.3%、k=12 85.3%、k=16 83.6%。同じなので k = 10。dev では差が出なかった。
- test（1回）: 1位 85.7 → 87.1%（+1.4、95%CI 0.0〜+3.2）、回す率 20.7 → 18.0%（−2.7、−5.1〜−0.9）。良くなった 3・悪くなった 0。言い換え: 1位 81.0 → 81.6%、回す率 25.5 → 24.3%。
- 判定: **採用**。1つ目の条件（1位の差の CI の下限 > 0）は下限がちょうど 0 で満たさないが、2つ目の条件（1位の差 ≥ 0 で、回す率の差の CI の上限 < 0）を満たす。言い換えも下がらない。
- 製品で増えるもの: LARM で採点する組が 1件あたり 7 → 10。LARM の推論の時間は組の数にほぼ比例すると見ているが、本番機では測っていない。
- 入れたもの: `src/scoring/best-v2.ts`（`BEST_V2_PARAMS` の形式 v2 の `extra.tools`、入力の `ranking`）、`src/retrieval/sr.ts`（`srRanking`）、`BEST_V2_PARAMS`（source `4442fe7939835c60`、回す閾値 0.2989）。best_v2.py の設定 `best-v2+k10`、`select`（dev だけで設定を選ぶ）、`srfull.ts`（全カードの順位）。
- 確かめたこと: best_v2.py とパッケージの判定が test＋言い換え 1,432件で一致（追加の候補を含む）。パッケージだけの経路で test 87.1 / 18.0・言い換え 81.6 を再現。bench の `router route` も test 217件で並びが全件一致。
- 途中で直したこと: 記憶の近傍（kNN）の計算を、Python でも float64 と安定な並べ方にした（パッケージと同じ）。10件目と11件目の近さの差が 1×10⁻⁷ の件で、float32 の和だと選ぶ例が入れ替わり、追加の候補（browser.operate）の票が変わっていた。今までの版の並びは変わらない（確率の差 ≤ 4.2×10⁻⁸）。LARM が採点しない 400字超えの文には追加の候補を足さない（学習と同じ）。
- 実測: `docs/reports/data/2026-11-03/improve/c2-k10.compare.json`、`docs/reports/data/2026-11-03/best-v2-larm2-k10.ranked.jsonl`。
- 独立した見直し（1回）: パッケージの判定に正しさの誤りはなかった。bench 側の指摘を直した: 設定 k で全カードの順位が無いときは止める（黙って追加の候補なしで学習しない）、検索の上位にある担当は追加の候補にしない（TS と同じ）、`srRanking` の最大値をループで計算する、`router route` の候補にも種類ごとの上限をかける、新しく書いたスクリプトの埋め込みのモデル名を引数にする（`router route` は `--model` が必須になった）。直した後も、全カードの順位・基準と k=10 の並び・`router route` の test 217件・学習の対のハッシュが同じ。
- 注記: 記憶の近傍の計算を float64 にしたので、それより前の記録（best-v1、学習なしの ruri の best-v2、旧 network の版）は、bench で再計算すると確率の下の桁が変わりうる（再計算はしていない）。

## 5. 分けたほうが良いときだけ分ける（不採用、2026-11-04）

- 計画: 構造の判断（今は S3）の結果を、best-v2 の自信（1位と2位の差、回す閾値）で確かめる。参照つきの単一の依頼は、伏せた文の自信が元の文以上のときだけ伏せた文の担当を採る。依頼なしは、元の文が自信のある担当（会話以外、回さない）なら担当を残す。複数の依頼は、部分がどれも回さない自信のときだけパイプラインへ。設定の値はない。比べる相手は、候補 2 を採用した版（ツールの候補 10件）での S3・mask。
- 結果: 作った対 186件の「送り先と担当が合う」 90.3 → 83.9%（−6.5、95%CI −10.2〜−2.7、良くなった 1・悪くなった 13）。依頼なし → 会話 100 → 64.7%、複数 → パイプライン 84.5 → 74.1%、参照の側に送る 1.3 → 5.2%。test 217件の1位 88.5 → 88.5%（0、−2.3〜+2.8、良くなった 4・悪くなった 4）。正しい構造（S*）に重ねても 94.6 → 86.6% に下がる。
- 判定: **不採用**（作った対ではっきり悪くなり、test は変わらない）。
- 根拠: best-v2 の自信は、参照の語に引かれた誤りでも高く出る（「この音楽に合う画像」を文全体で振り分けると、音楽を自信を持って選ぶ）。感想の文（「この曲いい感じ」）も自信を持って担当に送る。だから、自信は「分けるかどうか」の審判にならない。分けるかどうかは構造の判断そのものの精度で決まる。
- 同じ測定で分かったこと（採用した版での基準の値）: 作った対で S0 51.6%（参照の側 15.6%）、S3・mask 90.3%。test 217件で今の経路 189件（87.1%）→ S3・mask 192件（88.5%、差の 95%CI −1.4〜+4.1）。
- 実測: `archive/structure-judgment/results/2026-11-03/c5-check.report-pairs.json`、`c5-check.report-test217.json`。コード（`decideChecked`）は消した。対応のあるブートストラップの `pairedCi` は残した。

## 4＋3. 係り受け解析で構造を取る（S1）、参照の種類の手がかりは文全体のときだけ使う（不採用・条件未達、2026-11-04）

- 計画: GiNZA（`ja_ginza` 5.3.0）の係り受けに規則をかけて構造を作る（`archive/structure-judgment/s1.py`。解析器は同じプロセスの中で読み、サーバーは立てない）。候補 3 は、構造の判断で参照を伏せた文と部分には手がかり（`referencedResource`）を渡さず、文全体を振り分けるときだけ渡す。構造の評価セットを dev・test に半分ずつ分け（対は同じ側、対の id のハッシュ。実際の発話は bench の split）、規則は dev 半分（作った対 87・実際の発話 4）だけを見て作った。比べる相手は、本番と同じく手がかりを渡す今の経路（S0＋手がかり、ツールの候補 10件の版）。
- dev で作った規則: 依頼は主節の述語（文の根か、読点・文末・「から」が続く「〜て」「〜たら」、目的語を持つ「〜て」）で依頼の形のもの。名詞句の中の動詞（「画像を作るタスク」）は依頼にしない。「〜を使って、」は手段。「と」「も〜も」で並ぶ目的語は別の依頼。参照は指示語の名詞句（この・その・さっきの、それ・そこ）、「〜に合う・ぴったり・ふさわしい」の相手、「〜の雰囲気・イメージ・世界観・テイスト・感じで」。依頼の目的語そのものは除く。依頼が1つなら文全体から参照を拾う。後ろの文は接続の語（あと・それと・ついでに・次に…）で始まるときだけ新しい依頼、そうでなければ前の依頼の細かい指示。依頼の形がなく感想・質問の終わり方なら依頼なし。dev（作った対）: 96.4%、参照の側 0%、複数 → パイプライン 95.0%、単一 → パイプライン 0%。

- 判定: **不採用（条件未達）**。今の経路より大きく良い（作った対で +39.8 ポイント）が、参照の側・複数・単一の基準と、test 217件の1位を下げない条件を満たさない。
- 根拠（test 217件で下げた件。規則は直していない）: 長い説明文の「〜ていて」（説明）を依頼に数えて 4件の依頼にした。答え方の指定「出典の URL を添えて」を別の依頼にした（2件）。言い直し「…と言ったよね？」を感想の終わり方と見て会話にした。並列の取り方を誤った（1件）。ブラウザの中の多段（「検索して…再生して」、5件、今の経路も誤り）は、利用者の判断（browser.operate で閉じる）を規則にまだ入れていない。
- 候補 3 について: 単独では採らない。作った対では手がかりが参照の側の誤りを増やす（10.8 → 16.2%）が、実際の発話の test 217件で手がかりのある 13件（すべて画像）は、手がかりを外しても結果が1件も変わらない（参考値、事前に決めた比較ではない）。構造の判断があれば「参照を伏せた文には渡さない」で済むので、S1 の次の版と一緒に扱う。
